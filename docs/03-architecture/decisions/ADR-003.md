# ADR-003: EIP-712 Release Signatures

**Document ID:** ADR-003  
**Title:** Standardizing Release Manifest Signatures with EIP-712  
**Status:** APPROVED  
**Deciders:** Blockchain Engineer, Security Architect, Protocol Architect  
**Date:** 2026-11-09  

---

## 1. Context and Problem Statement
When a publisher signs a release manifest containing the root hash of their JavaScript assets, how do we structure the signature to provide human-readable wallet prompts, chain-specific replay protection, and verifiable typed cryptographic security?

---

## 2. Decision Drivers
- Human-readability in hardware and software wallets (MetaMask, Safe, Ledger).
- Cross-chain and cross-contract replay protection.
- EVM smart contract native verification compatibility (`ecrecover`).

---

## 3. Considered Options
- **Option 1:** Raw byte ECDSA signing (`eth_sign`).
- **Option 2:** Personal sign prefixed string (`personal_sign`).
- **Option 3:** EIP-712 Typed Structured Data Signing.

---

## 4. Decision Outcome
**Chosen Option:** **Option 3: EIP-712 Typed Structured Data Signing.**

We define a strict EIP-712 domain separator:
- `name`: "LUCENTRA"
- `version`: "1"
- `chainId`: [Target Network ID]
- `verifyingContract`: [PublisherRegistry Address]

And structured type:
`ReleaseManifest(string domain,string version,bytes32 manifestHash,uint64 timestamp,uint64 expiresAt)`

### Consequences
- **Positive:** Users and publishers see explicit, readable fields in wallet signing dialogues; cryptographically bound to domain and contract; full replay protection.
- **Negative:** Slightly higher implementation complexity than raw string signing.

---

## 5. Security Implications
Eliminates blind signing vulnerabilities. `eth_sign` is strictly banned due to phishing risks.
