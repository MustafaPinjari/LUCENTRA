# ADR-007: EAS Release Attestations

**Document ID:** ADR-007  
**Title:** Using Ethereum Attestation Service (EAS) for Release Attestations  
**Status:** APPROVED  
**Deciders:** Blockchain Engineer, Protocol Architect, Security Architect  
**Date:** 2026-11-09  

---

## 1. Context and Problem Statement
How should publisher release attestations (certifying that a specific `manifestHash` is authentic for a domain) be recorded on-chain in an open, composable, and standardized manner?

---

## 2. Decision Drivers
- Industry standard attestation infrastructure.
- Pre-built indexers, GraphQL endpoints, and explorer UIs.
- Native on-chain revocation support.
- Avoid reinventing custom attestation contracts.

---

## 3. Considered Options
- **Option 1:** Custom release storage inside `PublisherRegistry.sol`.
- **Option 2:** Raw transaction log event emissions.
- **Option 3:** Ethereum Attestation Service (EAS).

---

## 4. Decision Outcome
**Chosen Option:** **Option 3: Ethereum Attestation Service (EAS).**

We register a formal EAS Schema on EVM networks:
`bytes32 manifestHash, string domain, string version, bytes signature`

Publishers submit attestations directly to EAS. Each release receives an immutable 32-byte Attestation UID.

### Consequences
- **Positive:** Leverages existing EAS infrastructure, developer tooling, and public block explorers; supports native off-chain attestations with on-chain revocation.
- **Negative:** Dependent on EAS contract deployments across target networks.

---

## 5. Security Implications
Attestation validity requires verifying that the attestor is currently an authorized signing key for the specified domain in `PublisherRegistry.sol`.
