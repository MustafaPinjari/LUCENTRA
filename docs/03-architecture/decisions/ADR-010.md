# ADR-010: Off-Chain Manifest Storage

**Document ID:** ADR-010  
**Title:** Off-Chain Manifest Storage with Content Addressing and Root Digest Anchoring  
**Status:** APPROVED  
**Deciders:** Backend Engineer, System Architect, Blockchain Engineer  
**Date:** 2026-11-09  

---

## 1. Context and Problem Statement
A production web application manifest listing dozens of JavaScript bundles can easily exceed 10–50 kilobytes of JSON data. Storing this data directly inside an Ethereum smart contract incurs prohibitive transaction fees.

Where and how should the release manifest be stored and served?

---

## 2. Decision Drivers
- Zero gas overhead for large manifest payloads.
- High-speed delivery to client extensions.
- Absolute cryptographic binding to the on-chain attestation.

---

## 3. Considered Options
- **Option 1:** Direct EVM storage (Calldata or contract storage).
- **Option 2:** Pure IPFS storage.
- **Option 3:** Hybrid Off-Chain Manifest Storage: Stored in high-performance PostgreSQL/Redis/CDN, content-addressed and cryptographically verified by the on-chain `manifestHash` in EAS.

---

## 4. Decision Outcome
**Chosen Option:** **Option 3: Hybrid Off-Chain Manifest Storage.**

The raw canonical manifest JSON is stored in the LUCENTRA backend database and served via CDN/API. However, the client extension never trusts the backend payload blindly: it computes `SHA-256(canonicalize(manifest_json))` and confirms that the result matches the `manifestHash` attested in the publisher's on-chain EAS record.

### Consequences
- **Positive:** Instantaneous JSON delivery ($\le 80\text{ ms}$); zero on-chain storage cost; complete cryptographic immutability.
- **Negative:** If the off-chain storage is temporarily offline, clients must fall back to cached manifests or wait for IPFS/secondary mirrors.

---

## 5. Security Implications
Tampering with the off-chain manifest causes the client's computed `manifestHash` to mismatch the on-chain attestation, triggering an immediate security error.
