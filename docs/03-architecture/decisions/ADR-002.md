# ADR-002: Publisher Identity through Wallet and DNS Verification

**Document ID:** ADR-002  
**Title:** Dual-Anchor Publisher Identity via DNS TXT and Registrar Smart Contract Registration  
**Status:** APPROVED  
**Deciders:** Security Architect, Product Architect, Blockchain Engineer  
**Date:** 2026-11-09 (Updated: 2026-11-09)  

---

## 1. Context and Problem Statement
How does LUCENTRA securely and trustlessly bind a conventional web domain name (e.g. `uniswap.org`) to an Ethereum address without requiring changes to global DNS infrastructure, while preventing domain squatting, front-running, and unauthorized key claims?

---

## 2. Decision Drivers
- Zero changes to existing global DNS protocols.
- Proof of authoritative domain control via DNS TXT challenge.
- Elimination of front-running or arbitrary public domain claims on Ethereum.
- Separation of registrar registration role from publisher owner key management.
- Decentralized publisher sovereignty over release signing keys.

---

## 3. Considered Options
- **Option 1:** Well-known HTTPS file challenge (`/.well-known/lucentra.json`).
- **Option 2:** Publicly callable smart contract function with cryptographic tickets.
- **Option 3:** Registrar-Mediated On-Chain Registration: Off-chain DNS TXT validation followed by atomic registration via an authorized `Registrar` role, with publisher wallet sovereignty over key rotation.

---

## 4. Decision Outcome
**Chosen Option:** **Option 3: Registrar-Mediated On-Chain Registration.**

1. **DNS TXT Challenge:** Publisher requests a challenge token and adds a TXT record at `_lucentra-verification.<domain>`.
2. **Authoritative Resolution:** The backend verification service validates the record across authoritative nameservers.
3. **Registrar Submission:** The authorized registrar role invokes `registerDomain(domain, ownerAddress)` on `PublisherRegistry.sol`. No public registration function exists.
4. **Publisher Key Governance:** Once registered, the publisher owner address possesses exclusive authority (`onlyDomainOwner`) to authorize and revoke operational signing keys (`authorizeKey`, `revokeKey`). The registrar cannot touch signing keys.

### Consequences
- **Positive:** Front-running impossible; gasless for publisher during initial registration; strict separation of duties; auditable registrar logs.
- **Negative:** Requires trusted registrar operational key; mitigated by bounded registrar capabilities and governance multisig rotation.

---

## 5. Security & Trust Assumptions
- The registrar can only register unclaimed domains; it cannot reassign or alter existing domain owners or signing keys.
- If the registrar key is compromised, contract owner (multisig) executes `setRegistrar(newRegistrar)`.
